    Building a provider

    A provider adds something to Music Assistant: a music source, support for a kind of player, a metadata source or a plugin. A provider can live in two places, and what each asks of you differs.

    Two places

    In the server repository: a built-in provider

    A built-in provider ships with every Music Assistant server, and the team keeps it working through every change to the server. Because the project supports it for years, a new built-in provider asks for:

    • demand you can show: users who want it, beyond yourself;
    • a pull request on the user documentation that describes it;
    • code that follows the code standards of the server and the usage policy, with tests;
    • a named maintainer (you) who follows up on issues and on changes to the service, the device or the server.

    You work in a fork of the server, and a maintainer reviews the new provider against the usage policy. After that, you merge most changes to your own provider yourself through the review bot. A built-in provider whose maintainer no longer follows up may be moved to the community catalog; that is announced first, so someone can take it over. The contributing guide and the developer guide of the server have the details, and the front page of this site sets up a development environment for the server.

    In your own repository: a community provider

    A community provider lives in your own repository, with your own documentation, support and releases. Servers install it from the community catalog, a list the project keeps in the registry. Only an administrator sees the community catalog, in the Marketplace, after enabling it and accepting that everything in it is installed at their own risk; other users only see what was installed from it.

    The community catalog asks less than the server repository, and the project supports nothing in it:

    • a public repository with an open source licence;
    • releases that pass the automated checks;
    • a domain of its own (the unique id of the provider in its manifest.json, such as sample_music, not a domain name): not one the server uses or reserves, and not one another community provider has;
    • a provider that crosses none of the red lines below.

    A person decides once, at admission, about what the provider does. The code is not reviewed, and later releases reach users without anyone looking at them.

    The red lines

    The community catalog declines a provider at admission, and blocks it when it is found later, when it crosses one of the red lines in the community catalog rules, which also say what is allowed at the user's own risk.

    A server stops loading a blocked provider once its next daily check of the community catalog fetches the block; its users keep their settings and library. A blocked version is skipped the same way.

    The template

    The community provider template is where a community provider starts. It holds one small music source, a test that runs it in a real server, a development container and CI. Its README takes you from Use this template to a provider running in a server in a few minutes, with Docker and VS Code with the Dev Containers extension as the only requirements, on Windows, macOS or Linux.

    The template pins the server version you develop against, at a release tag or a commit, and installs it from its source, which gives you type checking, completion in your editor and the test fixture.

    What a release has to look like:

    • the provider is in a folder named after its domain, provider, or providers/<domain> in a repository with several providers;
    • the release is a GitHub release, not a pre-release, whose tag is the version with or without v, such as v1.2.0;
    • the requirements are package names with version specifiers, without URLs, markers or options, and come as wheels for the Python version and platform of the server: a package that only comes as source cannot be installed;
    • the manifest is plain JSON;
    • the icon is optional: an SVG of at most 5 KB that only draws; an icon that does not pass is left out.

    The registry lists the exact limits in What a provider needs.

    Once installed, a provider runs inside the user's server. It never writes into its own folder: the server checks that folder against the release and replaces it when it differs. Options are config entries (get_config_entries), values that repeat go in the server's cache (@use_cache, self.mass.cache), and files go in a folder of its own under self.mass.storage_path or self.mass.cache_path. Its requirements are installed next to the server's own packages and never replace one; a provider whose requirements clash is not loaded.

    Where users get help

    The support_url in the manifest is where you take questions and bug reports, such as the issues of your repository. The Get help button of the app, on the settings page of the provider and in its details in the Marketplace, opens it, and so does the link to its maintainers in the note the app shows before it installs a provider from the community catalog. Without a support_url, the server gives an installed community provider its repository as one, so questions reach you and not the support repository of Music Assistant. The app only follows a link that starts with https://.

    Testing

    In your repository

    uv run pytest runs the tests of the template: quick checks of the manifest, the texts, the requirements and the icon, and a test that boots a real server with your repository as its local provider folder. The fixture comes with the server: pytest_plugins = ["music_assistant.testing"] in tests/conftest.py gives a fixture mass, a started server in dev mode with your repository as its local provider folder. That server announces nothing on the network and listens only on the local machine; what your provider asks of its service still goes out, so replace that in a test where you need to. The fixture needs pytest-asyncio with asyncio_mode = "auto", and next to the server the requirements of its Sendspin provider (aiosendspin[server] and av, at the versions in the server's music_assistant/providers/sendspin/manifest.json), which the server starts at every boot. The template has all of this in place.

    scripts/run.sh, or the Run Music Assistant task in VS Code, starts a server in dev mode that loads your provider, so you can try it in the app. Outside the container, on macOS or Linux with uv and ffmpeg 8 or newer, this is:

    uv sync
scripts/run.sh

    Only a server in dev mode loads providers from a local folder.

    On your pull requests

    CI runs the lint, the type check, the spelling check and your tests, and calls the registry's reusable workflow check-provider.yml, which runs the same checks the community catalog runs on a release: the manifest, the requirements against a channel, and loading the provider in the server image of that channel. Loading installs the requirements and imports the module of the provider; it does not set the provider up and does not run your tests.

    On a Music Assistant server

    Before you release, you can try your provider on a real Music Assistant server that fetches it from GitHub. This server runs the nightly build of Music Assistant, and the community catalog does not have to be enabled on it. Your repository must be public, with the provider in a folder named after its domain, provider, or providers/<domain> in a repository with several providers. You name it in one of these forms:

    • owner/repo: its default branch;
    • owner/repo@ref: a branch, a tag or a commit;
    • owner/repo@pr-12: pull request 12 of that repository.

    The server fetches your repository again at every start, so a restart picks up new commits. Your provider then appears among the providers you can add, with the badge Community. When it does not, the log of the server tells why.

    Use a test server with data of its own, never the data of the server you use every day.

    On Home Assistant

    1. In the App store of Home Assistant, add the repository https://github.com/music-assistant/home-assistant-addon when it is not there yet, and install the Music Assistant DEV SERVER app.
    2. Stop the Music Assistant app if it runs: the two apps use the same network ports.
    3. In the Configuration tab of the DEV SERVER app, set Provider repository to your repository, such as your-github-handle/your-repository@my-branch, and start the app.
    4. Select Open Web UI and add your provider.

    The DEV SERVER app keeps data of its own, apart from the Music Assistant app. Its Log tab shows the log of the server; set Log Level to debug for more detail. To go back, stop the DEV SERVER app and start the Music Assistant app again.

    On Docker

    Stop any other Music Assistant server on the machine first: both would use the same network ports. Then start the development image with your repository and a volume of its own:

    docker run --rm --network host -v ma-dev-data:/data \
  -e PROVIDER_REPO=your-github-handle/your-repository@my-branch \
  ghcr.io/music-assistant/server:dev
    • Open port 8095 of the machine in a browser and add your provider.
    • The container prints the log of the server; add --log-level debug after the image name for more detail.
    • To restart, stop the container with Ctrl+C and run the command again.
    • To go back, stop the container and start your own server again.
    • docker volume rm ma-dev-data removes the data of the test server.

    Joining the community catalog

    You submit your provider with the form Submit a provider: its repository, and only when needed the folder and the tag prefix. The person who submits it must own the repository or be a code owner in the manifest of its latest release, and that release must pass the checks on at least one channel. The result of the checks appears as a comment on the issue. When every check passes, a registry maintainer reviews the provider against the rules and decides. The owner of the repository and the code owners in the manifest are the maintainers of the provider. The registry's README tells the rest.

    Moving a provider from the server. A code owner of a provider that ships with the server can move it to their own repository under the same domain: submit it with the box Moving from the server ticked. Once it is admitted, the team removes it from the server in the release whose community catalog offers it, and servers that use it then install your version and keep their settings. While the server still ships the domain, the test fixture and a server in dev mode do not load your copy: the server already has a provider by that name.

    Providers without a maintainer. A built-in provider whose maintainer no longer follows up is parked in a repository of the Music Assistant organisation and keeps being released through the community catalog. To take it over, say so on its issue "looking for a maintainer"; you then release it from your own repository under the same domain.

    What the nightly test reports

    You release whenever you want: publish a GitHub release, and nothing else is needed. The registry looks for new releases once a night: it takes the most recently published release of each listed provider, when it has not seen it before, and checks it. It also tests the newest versions of each provider again against the current server of every channel it tests: the nightly, the beta and the newest stable channel.

    • A version that passes on a channel is offered to the servers on that channel.
    • A version that fails, or that stops loading on a channel, is not offered there. Servers on that channel that run it switch to the newest version that still passes there; when none does, the provider stops loading there.
    • A release that is refused or fails, and a version that stops loading on a channel, are reported in one issue per provider on the registry, with the label release-check, the reason and the output of the failing check. The issue mentions the maintainers of the provider once, a later failure is added to it as a comment, and it closes by itself when a later release passes.

    With a beta that runs for several weeks, you usually know about a problem well before a stable release reaches your users. To support the stable release and follow the nightly at the same time, publish one version, wait until the registry has picked it up (it appears under providers/<domain>/ in the registry), and then publish the other. Each version is then offered where it passes.
